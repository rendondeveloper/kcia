# `kcia ask`: talk to the planner without starting a task

## Decisions already made

- The public command is **`kcia ask`**. Replace the current stub. Do not add `kcia answer`.
- **`kcia work answer` is out of scope.** Leave its name and behavior alone.
- This is a **conversation with the planner**, not a wave and not a third agent.
- Output is the planner's reply **on stdout**.
- Turns **continue** until the user clears them.
- The conversation can be **sent to `kcia work`** so that work starts from it.

## Analysis

`kcia ask` already exists as a stub (`commands/ask.py` → `NOT IMPLEMENTED`, help: "Run a
direct query without creating a task"). Root help even shows
`kcia ask "which profiles apply to lib/main.dart?"`. Nothing behind it runs a model.

Waves always create or continue a task, write `.ai/context/` files, and ship a large
prompt (role, full guardrails, profile references, wave template, blocked protocol).
Skills run the **builder** and are allowed to edit. Neither is a cheap, read-only,
iterative research loop.

`kcia ask` fills that gap:

- The user has a question about the project, wants something looked up in the repo or
  on the internet, or just wants to think out loud with kcia.
- Each invocation sends the prompt to the **planner** agent (`resolve_agents()["planner"]`).
- Python, not the model, gathers facts that have a single verifiable answer: project
  facts, repo map, related and recent session history, active-task snapshot if any.
- The planner may still use Read/Grep/Glob, and web tools when the user asked to
  investigate something outside the repo.
- Follow-up `kcia ask "…"` calls continue the same conversation.
- `kcia ask --clear` wipes it.
- `kcia ask --work` starts `kcia work` from the conversation, with no extra model call
  to rewrite the brief.

Provider adapters already support session resume (`RunRequest.resume` + `session_id`).
Wave runs currently pass `resume=False`. Ask should resume so follow-up turns do not
resend the whole prompt.

## Open questions

1. **`kcia ask --work` while a task is already active.** **Answer: refuse** — tell the user
   to `kcia work abort` first, or use `kcia work answer` to inject into the active task.

## Implementation (completed)

- Version: **0.19.0** (minor) — new `kcia ask` capability behind an existing stub.

### Command surface

Replace the stub. Same text-input shape as `kcia work`: positional words, `--file`/`-f`,
`--stdin`. Reuse `normalize_text` / the existing resolver.

```text
kcia ask "how does login work in this repo?"
kcia ask "and where are refresh tokens stored?"   # continues the same conversation
kcia ask --clear                                  # wipe conversation, no model call
kcia ask --work                                   # start kcia work from the conversation
```

Empty text with no flags → short usage, exit 1.

`--clear` and `--work` do not take a question in the same invocation. Combining either
flag with positional/`--file`/`--stdin` is an error.

This is **multi-invocation**, not an interactive REPL. A REPL is out of scope.

### Process

```text
kcia ask "<question>"
        │
        ├─ require git repo + `.ai/` (kcia init). Refuse if a wave lock is held.
        ├─ load `.ai/local/ask.json` (or start empty)
        ├─ Python: project.md, repo map, related+recent history, active-task snapshot
        ├─ run planner (read-only). Resume provider session when possible.
        ├─ print planner reply on stdout (progress on stderr)
        └─ append the user+planner turn to ask.json

kcia ask --clear
        └─ delete `.ai/local/ask.json`. No provider call.

kcia ask --work
        ├─ fail if there is no conversation
        ├─ Python concatenates the transcript into a work prompt (no extra LLM call)
        └─ same entry as `kcia work "<text>"` (create task + run until the approval gate)
```

Ask does **not** require an active task. A paused or active task is allowed during Q&A;
only a held wave lock blocks it (same as `kcia skill`).

### Continuity

Conversation lives in **`.ai/local/ask.json`** (already gitignored via `.ai/local/`).
Not the durable `.ai/history/sessions.jsonl` — that log is English, git-tracked, and is
for completed work.

```json
{
  "schema_version": 1,
  "provider": "cursor",
  "model": "composer-2.5",
  "provider_session_id": "…",
  "updated_at": "2026-08-25T13:35:00Z",
  "turns": [
    {"role": "user", "text": "…", "at": "…"},
    {"role": "planner", "text": "…", "at": "…"}
  ]
}
```

- First turn: `resume=False`. Persist `RunResult.session_id` when the adapter returns one.
- Later turns: if stored provider+model still match the current planner and a
  `provider_session_id` exists, call with `resume=True` and only the new user text (plus
  a tiny Python-refreshed facts prefix). If resume fails or the planner pair changed,
  rebuild from the local transcript (last **8** turns, truncated) and start a new
  provider session.
- `--clear` deletes the file and prints `Conversation cleared.` Exit 0. No provider
  call. The provider-side session is abandoned, not deleted (no reliable API for that).

The conversation is **not** English-gated. `session log` stays English-only; this is a
local, user-facing chat and may follow the user's language. The prompt template itself is
English.

Write a turn pair to disk only after a successful planner run, so Ctrl-C cannot leave a
half-written user turn.

### What Python puts in the prompt (keep it small)

New composer, **not** `build_prompt()` / wave templates. Do not include profile
references, wave instructions, or the blocked protocol.

| Section | Source | Bound |
|---|---|---|
| Role | Short: you are the kcia planner, read-only Q&A, no file writes, no git writes | ~150 tokens |
| Guardrails | `input-filter.md` + `tool-control.md` only | as on disk, both small |
| Project facts | `.ai/context/project.md` | already capped |
| Repo map | `build_repo_map` | manifest-derived |
| Related history | `index.search` on sanitized question words (reuse the understanding-wave sanitizer) | top **5**, title + first summary line ≤120 chars |
| Recent history | `index.list_recent(limit=3)` minus ids already in related | timestamp + title, so the model can prefer newer data |
| Active task | `Session.load` if present | id, title, current wave, status — omit if none |
| Prior turns | only when not resuming the provider session | last 8 turns, each turn capped |
| Question | the new user text | as given |

On **resumed** turns, send: short role reminder + refreshed related/recent history for
*this* question + the new question. Do not resend project.md, repo-map, or the full
transcript (the provider session already has them).

Extract a shared helper for the history search (today `_related_history` is private in
`waves/prompts.py`) so understanding waves and `ask` share one implementation.

Optional: if the question mentions a repo-relative path that exists and is under
`MAX_FILE_BYTES`, attach a truncated copy. Do not grep the tree from Python; the planner
still has Read/Grep/Glob.

Budget: compose with `estimate_tokens`; drop optional sections in order
`prior-turns` → `recent-history` → `related-history` → `repo-map` if the prompt would
exceed a **small** cap (e.g. 8k tokens, far below the 120k wave budget). The whole point
of this command is to be cheaper than a wave.

### Provider run

- Agent: **planner** from `resolve_agents`.
- `allow_edits=False` (same as understanding). Cursor/OpenCode therefore do **not** get
  `--force` / `--auto`.
- Claude: keep write tools disallowed; **allow** `Read`, `Grep`, `Glob`, `WebSearch`,
  `WebFetch` (and planner MCP tools already configured for that role). Web is available
  on every turn; the prompt says to use it only when the user asked to research or the
  repo cannot answer. No Python HTTP client.
- MCP: attach the planner's existing MCP config (same helper as understanding) so a
  Jira question can use Atlassian when enabled. Do not add a new MCP server for web.
- Progress: `WaveProgress` on **stderr**, `periodic_updates=True`, same as skills/waves.
- **Stdout:** the planner's `output_text` when the run finishes. That is the user-facing
  result. Do not write `task.md` / `plan.md`. Persist the prompt+output under
  `.ai/local/runs/ask-<timestamp>.*` for debugging (same pattern as skills).
- Ctrl-C: reuse `interruptible` / `should_cancel` like skills.

Prompt instruction (control-plane template `control-plane/prompts/ask.md.j2`): answer
from the supplied facts and repo tools; prefer session history with later timestamps
when facts conflict; use web tools when asked to investigate outside the repo; cite
paths and session titles; reply in the user's language; do not start waves unless the
user sent the conversation to work.

### Send the conversation to work

`kcia ask --work` (no new question):

- Fail if `.ai/local/ask.json` is missing or has no turns.
- **No extra planner call.** Python concatenates the transcript into a work prompt:

  ```text
  From a kcia ask conversation.

  ## Latest user intent
  <last user turn>

  ## Conversation
  ### User
  …
  ### Planner
  …
  ```

- Call the same `_create_task` + pipeline entry as `kcia work "<text>"` so the user does
  not retype anything. That starts understanding and continues until the approval gate,
  same as a normal `work` invocation.
- If a task is already active: follow open question 1.
- Do not auto-`--clear`. The chat stays until the user clears it.

  embed the full transcript; provider/model change rebuilds.
